## What was built

Added files:
src/astra_swarm/guardrails.py - input validation layer with three defences.

- validate_alert_input(): length cap (8000 chars), empty/type check, prompt-injection tripwire matching 7 regex patterns from public red-team datasets.
- TOOL_ALLOWLIST per worker: enrichment sees only ATT&CK tools, ITDR only auth-log tool, SOC analys sees only ATT&CK tools, assessment and evaluator see none.
- filtered_tool_schemas(): enforces the allowlist at each worker call site.

Updated files:
src/astra_swarm/graph.py

- guardrail_check_node: as first node after START, routes to guardrail_quarantine_node (new terminal node) on flagged input, otherwise to router
- guardrail_quarantine_node: separate terminal node from escalation_notification_node, cleaner semantic separation between "we investigated and it's severe" vs "we refused to investigate because input was suspicious"
- escalation_notification_node: updated to write escalated=True unconditionally when the escalation path runs, fixing the earlier semantic bug where the field only reflected ITDR auto-escalation rather than the actual escalation route taken
- IncidentState: added guardrail_flagged and guardrail_reason fields

src/astra_swarm/evaluators.py — four evaluators for both LangSmith and local paths:

- routing_correctness: binary check of predicted vs expected alert class
- severity_correctness: ordered severity comparison with partial credit for off-by-one
- trajectory_correctness: Jaccard similarity between required and actually-run specialist workers, with structural workers (assessment, escalation_notification, guardrail_quarantine) filtered from the comparison
- escalation_correctness: binary check of predicted vs expected escalation flag

evals/week5_golden_set.json — 20 alerts across all five routing classes, generated by Claude with strict structured output, human-reviewed pass covering expected_routing, expected_severity, expected_escalation, expected_workers_contains, and per-alert labeling notes. Four labels corrected during case review of routing failures.

scripts/run_eval.py — local eval runner built as fallback when LangSmith setup was blocked. Runs the graph against the golden set sequentially, computes all four evaluators, writes eval_report.json, exits non-zero on threshold regression. Includes per-alert try/except so single alert crashes don't abort the run.

.github/workflows/eval.yml — GitHub Action running the eval on every PR, uploading the JSON report as an artifact, failing the build on threshold violations. Thresholds set at routing 0.70, severity 0.70, trajectory 0.75, escalation 0.65 — roughly 10 percentage points below current baseline to catch real regression while tolerating variance.

notebooks/week5_milestone.ipynb — consolidation notebook showing the final scorecard and guardrail effectiveness on a small set of adversarial alerts.

## What worked

Supervisor prompt tightening on ITDR and SOC analyst produced measurable improvement. The Week 4 supervisor was over-calling both specialists — ITDR ran on 18 of 20 alerts regardless of routing class, SOC analyst ran on 15 of 20. After constraining ITDR to identity_auth routing (plus explicit auth-anomaly language in the alert text) and SOC analyst to alerts where enrichment had cited a lateral-movement/C2/exfiltration ATT&CK tactic, trajectory jumped from 0.69 to 0.84. Both criterion changes were single-line prompt edits.

The evaluator design pattern of "filter structural workers before comparing" made trajectory measurement honest. Switching to Jaccard and filtering out assessment, escalation_notification, and guardrail_quarantine from both sides gave the first real trajectory signal. Same lesson as Week 4's evaluator work: what a metric measures matters more than what it looks like.

Golden set case review paid off disproportionately. Reviewing 7 routing failures found 4 mislabeled alerts. Correcting those 4 labels moved routing 0.65 → 0.80, severity 0.68 → 0.80, escalation 0.65 → 0.75 simultaneously (the labels were wrong on multiple fields consistently). Data quality was hiding real system performance. This was the highest ROI activity of the sprint.

When LangSmith tracing couldn't be reliably enabled (see "What broke"), the local runner shipped as a functionally equivalent alternative. Same evaluators, same scoring logic, same JSON report, same threshold-based regression gate.

The escalated state field semantic fix. The Week 4 design had escalated=True set only by ITDR's confidence-based auto-escalation, but the escalation routing (severity-gated path) fired independently. Result: incidents that took the escalation branch had escalated=False in state, and the evaluator saw the graph as "not escalated" when it clearly had been. One-line fix in escalation_notification_node — always write escalated=True when the node runs — restored the semantic invariant.

## What broke

LangSmith setup was the dominant time sink initially. Cascade of issues:

Initial Service Key created worked for the LangSmith dashboard login but returned 403 on both read (list_projects) and write (create_run) API calls
An invisible whitespace was added in the copied secret value — LangSmith's UI adds a trailing character on copy depending on browser/font
Ghost scope-diagnostic run stuck in pending state; the manually-created diagnostic run needed explicit update_run(end_time=...) to close it.

Worker naming convention mismatch between graph state and golden set. The graph writes short names to workers_run (enrichment, soc_analyst); the golden set was generated with _worker-suffixed names (enrichment_worker, soc_analyst_worker) because Claude defaulted to node names. Fixed by normalizing the golden set to short names rather than adding suffix-stripping in the evaluator — kept the evaluator simple and made the ground truth honestly match what the system produces. Broader pattern: evaluators shouldn't hide convention mismatches; ground truth should match system output.

Eval crashes silently dropped alerts from LangSmith evaluate() aggregates. LangSmith's evaluate() handles target exceptions by recording the example as failed and continuing, but failed examples don't contribute to aggregate scores. Result: an eval reporting "14 of 20 scored" and computing averages over 14 makes the metric look artificially clean while hiding failures. Fixed by wrapping target() in try/except so every alert produces a scoreable shape (crashes score as zeros with a target_error field). Broader lesson: aggregate scores from any eval framework need a sanity check that total example count equals successful evaluation count.

LangSmith's client.list_runs() deprecation warning surfaced during diagnostic work. Not a blocker for the sprint but worth flagging for Week 6 when LangSmith integration gets revisited.

Prompt caching remained unaddressed. Same threshold miss noted.
